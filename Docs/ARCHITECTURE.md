# System Architecture & Cryptography — Penik Messenger

Penik Messenger — это кроссплатформенный мессенджер с поддержкой оконечного шифрования (End-to-End Encryption, E2EE), поддержкой нескольких устройств на аккаунт (Multi-Device), групповых чатов с эпохальными ключами, аудио/видеозвонков LiveKit 1:1, каталога стикеров с импортом из Telegram и встроенного защищённого хранилища для передачи зашифрованных медиафайлов.

---

## 1. Cryptography Architecture (Схема шифрования)

### 1.1. Личные сообщения (1:1 Direct Messages)
- **Протокол:** X25519 + HKDF-SHA256 + ChaCha20-Poly1305.
- **Алгоритмы:**
  - **Ключевой обмен:** X25519 (Curve25519).
  - **Деривация ключей:** HKDF-SHA256 с 32-байтной солью и инфо-тегом `penik-pairwise-message-v1`.
  - **Симметричное шифрование:** ChaCha20-Poly1305 (256-bit key, 96-bit nonce).
  - **AAD Binding (v1):** Дополнительные аутентифицированные данные связывают отправителя, получателя и временную метку сообщения, предотвращая replay-атаки между контекстами.
- **Multi-Device E2EE:**
  - Каждое устройство пользователя генерирует собственную пару ключей идентичности (`IK`).
  - При отправке личного сообщения клиент получает через REST API (`GET /api/v1/keys/bundle/:user_id`) бандл ключей **всех активных устройств** получателя (а также дополнительных устройств самого отправителя).
  - Сообщение зашифровывается **отдельно для каждого целевого устройства** (payload содержит массив зашифрованных блоков под `device_id`).

### 1.2. Групповые чаты (Group E2EE)
- **Модель эпохальных ключей (Epoch Keys):**
  - Каждый групповой чат имеет текущую версию ключа группы (`KeyVersion`).
  - Для каждой версии ключа создаются **зашифрованные конверты (Envelopes)** — эпохальный ключ группы зашифровывается персонально для каждого устройства каждого участника группы на парном X25519-секрете.
- **Ротация ключей (Key Rotation):**
  - При изменении состава участников (добавление/исключение пользователя или устройства) генерируется новая версия ключа группы (`KeyVersion + 1`).
  - Заново шифруются и распространяются конверты ключей для актуальных устройств.
- **Шифрование сообщений в группе и AAD v2:**
  - Сообщение группы шифруется ChaCha20-Poly1305 с использованием ключа текущей эпохи группы (`KeyVersion`), соль и nonce генерируются заново на каждое сообщение.
  - **Group AAD v2:** Бинарная структура AAD связывает:
    1. Версию AAD (`0x02`),
    2. ID группы (`uint64`),
    3. Версию группового ключа (`uint32`),
    4. ID сообщения (`length-prefixed string`),
    5. **ID отправителя** (`sender_user_id`, `uint64` — берется строго из авторитарного транспортного фрейма WebSocket/REST),
    6. Временную метку отправки (`int64`).
  - Это исключает подделку авторства сообщений сервером и перенос шифртекстов между группами.

### 1.3. Аутентификация ключей и TOFU Pinning
- **Safety Numbers:** 60-значный отпечаток пары публичных identity-ключей для ручной верификации между собеседниками.
- **TOFU Key Pinning:** Механизм Trust-On-First-Use: клиент запоминает открытый ключ собеседника при первом контакте и выдает предупреждение при изменении ключа (переустановка/новое устройство).

### 1.4. Резервное копирование ключей (Key Backups)
- Приватный identity-ключ зашифровывается мастер-паролем/фразой: PBKDF2 (600 000 итераций) → деривация 256-битного ключа AES-GCM.
- Сервер хранит зашифрованный blob без знания мастер-пароля.

## 2. Device Pairing (Связывание устройств и передача истории)

Новое устройство (например, веб-клиент) может быть привязано к существующему аккаунту (например, на Android) через QR-код.

1. **Создание сессии:** Новое устройство вызывает `POST /api/v1/pairing/sessions` и генерирует одноразовый публичный ключ X25519.
2. **Сканирование:** Основное устройство сканирует QR-код (содержащий `session_id` и публичный ключ) и вызывает `POST /api/v1/pairing/sessions/claim`.
3. **Передача истории:** Основное устройство зашифровывает локальную историю ключом, выведенным через ECDH (HKDF) с ключом сессии, и отправляет пакет через `PUT /api/v1/pairing/sessions/:id/history`.
4. **Импорт:** Новое устройство скачивает зашифрованную историю, расшифровывает её локально и сохраняет в локальную БД.

## 3. Attachments Architecture (Собственное защищённое хранилище вложений)

Для передачи медиафайлов и документов используется клиентское сквозное шифрование и защищённое локальное хранилище на сервере:

1. **Шифрование и загрузка:**
   - Клиент локально генерирует случайный 256-битный ключ и зашифровывает файл алгоритмом **ChaCha20-Poly1305** (`nonce + ciphertext + tag`).
   - Зашифрованный файл отправляется на эндпоинт `POST /api/v1/attachments/upload` с авторизацией Bearer Token.
   - Сервер присваивает файлу случайный 128-битный ID, сохраняет зашифрованный блоб в `UPLOAD_DIR/attachments/<id>.bin` и возвращает URL вида `/api/v1/attachments/file/<id>`.
2. **Передача ключа:**
   - Ключ расшифровки передаётся исключительно внутри E2EE-сообщения (`file.key`) между авторизованными участниками чата. Сервер не имеет доступа к ключу и содержимому файлов.
3. **Скачивание и стриминг:**
   - Скачивание выполняется через `GET /api/v1/attachments/file/:id` с поддержкой HTTP Range-запросов (`206 Partial Content`) для надёжной докачки при нестабильной сети.
   - В вебе для HTML5-видеоплеера Service Worker (`/sw-stream/<id>`) перехватывает поток, расшифровывает блоб и отдаёт чанки `206 Partial Content`.
   - В Android клиент расшифровывает файл во временный локальный кэш и передаёт в ExoPlayer.

## 4. Stickers Architecture (Стикеры)

- **Формат и хранение:** Стикеры хранятся на сервере в формате WebP/WebM (статические и видеостикеры).
- **Импорт из Telegram:** Эндпоинт `POST /api/v1/stickers/import/telegram` загружает стикерпак напрямую через Telegram Bot API, скачивая метаданные и конвертируя/сохраняя файлы на сервер.
- **E2EE передача:** Стикер отправляется как E2EE JSON payload (`type: "sticker"`, `pack_id`, `sticker_id`, `emoji`, `url`).
- **Клиенты:**
  - **Web:** Встроенный picker с вкладками «Недавние» (до 32 стикеров) и установленных паков, кнопка импорта, модалка пака. По клику — полноэкранный просмотр, по долгому нажатию/ПКМ — открытие стикерпака.
  - **Android:** Compose `StickerPickerBottomSheet`, `StickerPackDetailDialog`, кэш недавних в SharedPreferences, нативный рендеринг WebP через Coil без баббла сообщения.

## 5. 1:1 Calls Architecture (Звонки через LiveKit)

- **Сигнализация через WebSocket:** Опкоды `0x30`–`0x36` (`CALL_OFFER`, `CALL_INCOMING`, `CALL_ACCEPT`, `CALL_REJECT`, `CALL_END`, `CALL_TAKEN`).
- **Multi-Device Ringing:** Звонок поступает на все активные устройства вызываемого пользователя.
- **`CALL_TAKEN`:** Когда звонок принимается на одном из устройств, сервер рассылает остальным устройствам событие `CALL_TAKEN`, мгновенно прекращая звонок на них.
- **Failover:** Автоматическое переключение на резервный LiveKit-сервер (`LIVEKIT_FALLBACK_URL`) при недоступности основного.

## 6. Хранение данных (Persistence Layer)

### 6.1. Сервер (Go Backend)
- **База данных:** SQLite в режиме WAL (`modernc.org/sqlite`).
- **Безопасность сессий:** Сессионные токены хранятся исключительно в виде криптографических SHA-256 хешей (`token_hash`).
- **Сохраняемые сущности:**
  - `users` (учетные данные, хеши паролей Argon2id, публичные имена, никнеймы).
  - `devices` (устройства, публичные ключи IK).
  - `sessions` (`token_hash`, `device_id`, время жизни, отзыв).
  - `chats` & `messages` (метаданные и зашифрованные конверты сообщений).
  - `groups`, `group_members`, `group_key_versions`, `group_key_envelopes`, `group_messages`.
  - `sticker_packs`, `stickers`, `user_stickers`.
- **Защита аватаров:** Чтение заголовков через `image.DecodeConfig` с проверкой габаритов (защита от бомб декомпрессии).

### 6.2. Android клиент
- **База данных:** Room + SQLCipher (полное шифрование локальной БД на диске).
- **Секреты:** Android Keystore / EncryptedSharedPreferences для приватных ключей.
- **Сеть:** Retrofit (REST), OkHttp (WebSocket), Hilt (DI).

### 6.3. Веб-клиент (Browser)
- **Хранилище:** IndexedDB с запечатыванием приватных ключей через WebCrypto non-extractable master key (vault).
- **Криптография:** Web Crypto API + WebAssembly (`libsodium`).
