# План разработки Android-клиента для Penik Messenger

Этот документ описывает техническую спецификацию, архитектуру и пошаговый план разработки нативного Android-клиента для мессенджера Penik. 

С учетом перехода на **No-E2EE** архитектуру (ветка `Noe2ee`), Android-клиент освобожден от сложной интеграции Signal Protocol (Double Ratchet) и взаимодействует с сервером напрямую через текстовые сообщения в бинарном WebSocket-протоколе (MessagePack) и стандартные REST эндпоинты.

---

## 1. Технологический стек

Для обеспечения высокой производительности, современного дизайна и реактивности предлагается следующий стек:

* **Язык разработки:** Kotlin
* **UI-фреймворк:** Jetpack Compose (для декларативного интерфейса и плавной анимации)
* **Архитектурный паттерн:** MVVM (Model-View-ViewModel) + Clean Architecture
* **Сетевой уровень (HTTP):** Ktor Client или Retrofit + OkHttp
* **WebSocket-соединение:** OkHttp WebSocket (с поддержкой отправки/приема бинарных фреймов `ByteString`)
* **Сериализация данных:** 
  * JSON (для REST API): `Kotlinx.serialization`
  * MessagePack (для WebSocket): библиотека `org.msgpack:msgpack-core` или Jackson с MessagePack-плагином для JVM.
* **Локальная база данных (кэш сообщений):** Room Database (аналог IndexedDB в веб-версии)
* **Асинхронность и потоки данных:** Kotlin Coroutines & Flow (StateFlow, SharedFlow)
* **Внедрение зависимостей (DI):** Dagger Hilt
* **Хранение токенов:** EncryptedSharedPreferences (для безопасного хранения токена сессии)

---

## 2. Архитектура приложения

Приложение будет разделено на 3 логических слоя (Clean Architecture):

```
+-------------------------------------------------+
|               Presentation (UI)                 |
|      (Jetpack Compose, Screen ViewModels)       |
+-----------------------+-------------------------+
                        |
                        v
+-------------------------------------------------+
|                    Domain                       |
|          (Use Cases, Business Models)           |
+-----------------------+-------------------------+
                        ^
                        |
+-------------------------------------------------+
|                     Data                        |
|       (Repositories, Room DB, Network API)      |
+-------------------------------------------------+
```

1. **Presentation Layer (UI):** 
   - `MainActivity.kt` — единственная точка входа (Single Activity).
   - Compose Screens (Auth, ChatsList, ChatRoom, UserProfile, Settings).
   - ViewModels, управляющие UI State (`StateFlow`) и обрабатывающие пользовательские намерения.
2. **Domain Layer:**
   - Бизнес-модели (`User`, `Chat`, `Message`).
   - Use Cases (интеракторы) для отправки сообщений, загрузки истории, авторизации.
3. **Data Layer:**
   - Репозитории, координирующие работу локальной БД (Room) и сети (HTTP/WebSocket).
   - Room Entity и DAO для таблиц `messages`, `chats`, `contacts`.
   - Сетевые сервисы (`WebsocketService`, `ApiService`).

## 4. Пошаговый план реализации

### Этап 1: Scaffolding и Базовая инфраструктура (1-2 дня)
1. Настройка сборки Gradle (`build.gradle.kts`): добавление зависимостей Compose, Room, Hilt, OkHttp, MsgPack.
2. Создание структуры пакетов (`data`, `domain`, `ui`).
3. Инициализация Hilt (`Application` класс, DI модули для DB и Network).
4. Настройка системы навигации (Jetpack Compose Navigation).

### Этап 2: Локальное хранилище — Room DB (2 дня)
1. Описание сущностей баз данных (`MessageEntity`, `ChatEntity`, `ContactEntity`).
2. Создание DAO с поддержкой реактивных Flow-запросов:
   * Выборка сообщений чата: `fun getMessagesForChat(chatId: String): Flow<List<MessageEntity>>`
   * Обновление статусов доставки (отправлено / получено).
   * Выборка списка чатов с последним сообщением и сортировкой по времени.

### Этап 3: Сетевое взаимодействие и WebSocket Сервис (3 дня)
1. Реализация REST API клиента через Retrofit/Ktor.
2. Создание `WebSocketManager` на базе `OkHttpClient`:
   * Метод подключения, автоматического переподключения (Exponential Backoff).
   * Фоновый цикл PING/PONG.
   * Парсинг входящих бинарных пакетов: определение Опкода по первому байту -> распаковка MessagePack payload.
   * Отправка сообщений (`0x01` опкод).

### Этап 4: Интеграция логики синхронизации (Sync Engine) (2 дня)
1. Обработка `OFFLINE_BATCH` (`0x05`): сохранение пачки сообщений в Room, отправка `0x04` (MSG_DELIVERED) на каждое.
2. Фоновый `syncMessageHistory()`:
   * Запрос из Room максимального `id` полученного сообщения.
   * HTTP запрос истории `/messages/history?after_id=...`.
   * Сохранение пропущенных сообщений в БД.
3. Обработка подтверждений `0x03` (MSG_ACK): обновление временного ID сообщения (`tmp-xxx`) на серверный ID и смена статуса отправки в UI.

### Этап 5: UI Разработка (4-5 дней)
1. **Экран авторизации:** Ввод логина/пароля, переключение Вход/Регистрация. Сохранение токена.
2. **Экран списка чатов:** Список диалогов с аватарами (загрузка через Coil), отображением последнего сообщения, счетчиком непрочитанных.
3. **Экран чата:** 
   * Отображение списка сообщений (LazyColumn) с автопрокруткой вниз.
   * Пузыри сообщений (отправитель справа, получатель слева).
   * Поле ввода с поддержкой автоизменения высоты (Multi-line).
   * Индикаторы доставки (одна галочка / две галочки).
4. **Профиль и Настройки:** Смена имени, загрузка нового аватара.

### Этап 6: Тестирование и Полировка (2 дня)
1. Тестирование сетевых сценариев: переход из Wi-Fi в LTE, потеря сети во время отправки, восстановление соединения.
2. Проверка работы фоновых уведомлений / доставки в фоновом режиме.
3. Оптимизация производительности (списки сообщений не должны лагать при быстрой прокрутке).

## 5. Риски и ключевые моменты
* **MessagePack парсинг в Kotlin:** В JVM/Android MessagePack не так популярен, как в Go/JS. Важно написать корректный сериализатор на базе `org.msgpack:msgpack-core`, чтобы не было несовместимости типов с бэкендом (например, знаковость чисел, соответствие big-endian).
* **Синхронность WebSocket-событий:** Нужно гарантировать, что сообщения из WebSocket обрабатываются в одном потоке/очереди базы данных, чтобы исключить состояние гонки при обновлении UI.
