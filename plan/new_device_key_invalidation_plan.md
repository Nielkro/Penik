# План решения: Синхронизация и инвалидация ключей при добавлении новых устройств

## 1. Проблема
Когда пользователь авторизуется с нового устройства, у него генерируется новая ключевая пара X25519 (`device_id`, `identity_key`).
Собеседники, которые уже вели с ним диалог, имеют в памяти закэшированный бандл его устройств (на 10 минут в Web и на 2 минуты в Android). 
При отправке новых сообщений:
1. Отправитель шифрует payload только под известные ему старые устройства получателя.
2. Новое устройство не получает персонального шифротекста или получает шифротекст, адресованный чужому `device_id`, и не может его расшифровать.
3. Проблема исчезает только после того, как новое устройство само отправит сообщение собеседнику, принудительно обновив кэш ключей (`forceRefresh = true`).

---

## 2. Архитектурные варианты решения

### Вариант А: Серверное WebSocket-оповещение об изменении устройств (Event-driven)
При регистрации нового устройства или публикации ключей (`POST /api/v1/keys/identity` / `OpKeyPublish`):
1. Сервер находит всех активных собеседников пользователя (через таблицу `chats` и активные WebSocket-сессии в `hub.go`).
2. Сервер рассылает легковесный фрейм события `OpUserDevicesChanged` (например, opcode `0x1B` или presence-модификатор) с `user_id`.
3. Получившие фрейм клиенты инвалидируют кэш бандла (`bundleMemoryCache.delete(userId)` в Web и `bundleCache.remove(userId)` в Android).

### Вариант Б: Протокол повторного запроса ключа (OpMsgRetryReq / OpMsgRetryResp)
В протоколе Penik уже зарезервированы опкоды `OpMsgRetryReq` (0x19) и `OpMsgRetryResp` (0x1A):
1. Если новое устройство получает сообщение, в котором нет шифротекста под его `device_id`:
   - Устройство отправляет отправителю запрос `OpMsgRetryReq(msg_id, recipient_device_id)`.
2. Отправитель, получив `OpMsgRetryReq`:
   - Принудительно сбрасывает кэш бандла для этого пользователя (`forceRefresh = true`).
   - Дошифровывает сообщение для нового `device_id` и возвращает `OpMsgRetryResp`.
*Плюс:* работает даже если WebSocket-уведомление было пропущено из-за оффлайна.

### Вариант В: Валидация списка устройств на сервере (Server-side Stale Bundle Check)
При обработке `OpMsgSend`:
1. Сервер сравнивает список `msg.Devices` получателя со списком фактически зарегистрированных активных девайсов получателя в БД.
2. Если у получателя появились новые устройства, которых нет в запросе отправителя, сервер отвечает ошибкой/Nack со статусом `STALE_KEY_BUNDLE` и актуальным списком девайсов.
3. Отправитель сразу обновляет бандл, перешифровывает сообщение и отправляет снова.

## 3. Рекомендуемый комбинированный план реализации

### Этап 1: Серверные уведомления и сброс кэша (Быстрый фикс)
- [ ] Добавить в `server/internal/ws/protocol.go` событие `OpPeerDeviceAdded` (или использовать broadcast в связанные чаты).
- [ ] В `server/internal/handlers/auth.go` и `server/internal/ws/client.go` при регистрации нового устройства вызывать broadcast в хаб для всех пользователей, имеющих общий `chat_id` с этим пользователем.
- [ ] В `client/js/app.js` и `client/js/ws.js`: по приходу события вызывать `bundleMemoryCache.delete(String(userId))`.
- [ ] В Android `MessageRepository.kt` и `WebSocketEventCoordinator.kt`: по приходу события удалять запись из `bundleCache[userId]`.

### Этап 2: Протокол самовосстановления (Retry Flow)
- [ ] В `client/js/app.js` и Android `MessageRepository.kt`: если в `MsgRecvEncrypted` поле `RecipientDeviceID` не совпадает с локальным `myDeviceId` или дешифрование не удалось:
  - Отправлять `OpMsgRetryReq` автору сообщения.
- [ ] На стороне автора: при получении `OpMsgRetryReq` подгружать свежий бандл и отправлять персональный шифротекст для нового устройства.
